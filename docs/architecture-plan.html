ArtistPin at scale

00

Where we are today

One phone, one database, no concept of "whose data this is."

Every show lives in a local Room database. ConcertRepository.saveEvent() finds-or-creates a city, a venue and a set of artists by natural key, then writes one event row and its artist cross-refs in a single transaction. It's a good design — it just assumes there is exactly one user, sitting on exactly one phone, forever.

Three things about the current build won't survive contact with a second phone, let alone a thousand:

  • The Spotify client secret is compiled into the APK (BuildConfig.SPOTIFY_CLIENT_ID/SECRET) — fine when only you can decompile it, not once the app is public.
  • Every phone does its own artist lookups. MusicBrainzGenreSource throttles itself to one request per second per device — a thousand devices looking up the same artist is a thousand times the work for an answer that never changes.
  • Photos live in this phone's private storage via MediaImporter. There is no second copy anywhere.
01

The core idea: split catalog from library

Most of what's in the database isn't actually yours.

Bedouin's Spotify image and genre tags are true for every user who has ever seen them — they don't belong to you any more than the venue's street address does. The only thing that's actually personal is the fact that you stood in front of them on a given night. Today's schema already gestures at this split without naming it: findByName, findCity and findVenue exist specifically so a second show at a known venue reuses the row instead of duplicating it. At scale, that same lookup just needs to happen against everyone's data, not one phone's.

So the schema splits in two:

  • Catalog — artists, venues, cities. Global, deduplicated by name, owned by nobody. Looked up once, reused by everyone.
  • Library — events, event_artist. Private, each row stamped with a user_id, referencing the catalog by id.

This is also what makes the scaling math work: with 10,000 users but 40,000 distinct artists between them, you run roughly 40,000 Spotify/MusicBrainz lookups ever — not 10,000 × (however many artists each person adds). The catalog only grows when someone adds a genuinely new artist or venue; everyone after that gets a cache hit.

02

Target architecture

The phone stops being the database and becomes a client of one. Room doesn't disappear — it becomes a local cache and an outbox for writes made offline (more on that in §03) — but the durable copy of every user's data lives behind a backend API.

Two details worth calling out because they fix concrete problems in the app as it stands today:

  • Keys move server-side. The Spotify client secret leaves BuildConfig entirely — the backend holds it, the phone never sees it.
  • Third-party calls become one-time, not one-per-phone. The MusicBrainz 1-req/sec throttle in MusicBrainzGenreSource stops being a per-device constant and becomes a backend job queue — still throttled, but shared across the whole catalog instead of duplicated by every phone that happens to add the same DJ.
03

Sync has to survive a bad venue signal

Adding a show usually happens standing in a club, not on wifi. The save can't wait on a network round trip — it has to feel exactly as instant as it does today. Concerts also aren't collaboratively edited: nobody else is racing you to log the show you just left, so the sync model can be genuinely simple — an outbox, not a conflict-resolution engine.

Step 4 is doing the same job findCity/findVenue/findByName already do locally — it just runs against everyone's catalog instead of one phone's copy. Nothing about that lookup is new work; it's the existing pattern, moved.

04

Migrating what's already on your phone

You already have an export path: the backup feature writes exactly the shape of data a migration needs — every show, artist, venue and city, as JSON, produced by BackupRepository. The first account ever created on the new backend can be seeded by running that same export through the backend's import endpoint once, rather than typing 50 shows back in by hand.

That also means the backup feature doesn't get retired once sync exists — it's repurposed as the one-time bridge, and can stay on afterward as a personal export/download option independent of the account system.

05

Phased rollout

Ordered so each phase ships something real on its own — none of it is a dead end if the next one gets delayed.

Five phases, in order
PhaseShipsWhy this order
00 Move the Spotify secret behind a thin proxy — even a single serverless function. Pure security fix. Needs no accounts, no sync, no schema change — and it's the one item that gets more dangerous the longer it waits.
01 Sign-in, backend skeleton, catalog/library split in Postgres. Single device, always-online. This alone is "many users, safely" — private shows, shared catalog. No offline handling yet, so it's the smallest slice that's genuinely multi-user.
02 Room becomes a real cache + outbox; background sync, per fig. 3. Now the app works the way it does today at a show with no signal — this is the phase users would actually notice if it were missing.
03 Photos move to object storage via presigned uploads; thumbnailing; per-user quota. Media is the expensive, slow-changing part — worth doing once the write path (phases 1–2) is trusted.
04 Optional, later: anything social — "who else was here," shared show pages. Explicitly outside today's spirit (a personal tracker, not a feed). Only worth it if it's actually wanted, once 00–03 are solid.
Not everything moves to the backend Sort order for the artist list is stored on-device via DataStore today, and should stay that way — it's a device preference, not content. Scaling the data doesn't mean centralizing every setting; only what's actually shared or actually needs a second copy has to leave the phone.
06

Choosing what runs the backend

The schema is already relational — cities, venues, artists, events, cross-refs, exactly the shape Postgres wants. That rules out a document-store rebuild being worth the trouble, and points at one of three routes:

Backend options, for a one-developer team
SupabaseFirebaseCustom (Node + Postgres)
Postgres directly — today's schema ports over with almost no reshaping. Firestore is document-based — the catalog/library split has to be re-modeled around collections. Postgres directly, same as Supabase — but you write and operate the API layer yourself.
Row-Level Security maps cleanly onto "your events are private, catalog is public-read" — enforced by the database, not app code. Security rules are written per-collection in a separate DSL — workable, but a second thing to keep in sync with the schema. You write the authorization checks yourself, in your own API code.
Auth, Storage and a Postgres instance bundled — one thing to run. Auth and Storage bundled; excellent free tier for early growth. Nothing bundled — auth, storage and hosting are each a separate decision.
Lock-in is mild — it's plain Postgres underneath; exportable at any time. Lock-in is real — Firestore's data model doesn't export cleanly to a relational shape later. No lock-in at all — and no guardrails either.
Recommendation

Supabase. The schema you already have — CityEntity, VenueEntity, ArtistEntity, EventEntity, EventArtistCrossRef — is close to a direct copy of what phase 01 needs in Postgres. Row-Level Security gives you the catalog/library ownership boundary from fig. 1 as an enforced database policy on day one, not application logic you have to get right in every code path that touches the data.
